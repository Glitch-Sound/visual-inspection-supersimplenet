## Purpose

<!--

誰が、どの場面で、何を達成し、その結果から何を判断または実行できるようになる能力かを、
1～2文かつ50文字以上で記述する。機能名だけでなく、利用者・運用者にとっての価値まで示す。
業務固有の用語や、結果を表す状態・区分が初見では分かりにくい場合は、続けて次の表を記載する。
実装方式、クラス、関数、ライブラリ、ファイル配置は記載しない。
-->

<利用者または運用者が、利用場面で得られる結果と、その結果を使って行える判断を記述する。>

<!-- 必要な場合だけ記載し、不要なら表を削除する。 -->

| 用語・結果 | 非開発者向けの意味 | 利用者・運用者による扱い |
| --- | --- | --- |
| <業務用語、状態、判定区分など> | <技術知識を前提にしない説明> | <表示後の判断、次の操作、引き継ぎなど> |

## ADDED Requirements

<!--
新しい要件を記述する。既存要件の変更は `## MODIFIED Requirements`、廃止は `## REMOVED Requirements`、
名称だけの変更は `## RENAMED Requirements` を使う。使用しない予約節は削除する。

要件本文は EARS (Easy Approach to Requirements Syntax) で書く。1つの Requirement は1つの検証可能な
規範的振る舞いだけを表す。曖昧な語 (適切に、可能な限り、通常は等) や実装のクラス・関数・DB・
ライブラリは書かない。業務用語、利用者・外部システムが与える入力、観測できる出力・状態・期限・
エラー種別を必要に応じて定義する。

- 常時: `システムは、<結果>しなければならない。`
- イベント駆動: `システムは、<トリガー>時に、<結果>しなければならない。`
- 状態駆動: `システムは、<状態>の間、<結果>しなければならない。`
- 条件付き: `システムは、<条件>の場合、<結果>しなければならない。`
- 例外・禁止: `システムは、<条件>の場合、<結果>してはならない。`
- 複合: `システムは、<状態>の間、<トリガー>時に、<結果>しなければならない。`
-->

### Requirement: REQ-001 <利用者価値が分かる日本語の要件名>

システムは、<EARS パターンに従う、単一で検証可能な要求>しなければならない (MUST)。

<!--
要件本文だけでは利用者・運用者が結果を判断しにくい場合、次の項目を必要な範囲で記載する。
proposal.md の役割・業務フローと同じ用語を使い、同じ内容を長く繰り返さない。実装方法は書かない。
-->

- **対象者**: <この結果を利用または処理する役割。外部システムの場合はその名称>
- **利用場面**: <いつ、何を目的に利用するか>
- **入力・開始条件**: <利用者が用意するもの、開始できる状態>
- **受け取る結果**: <表示、通知、保存状態、判定区分、期限など、確認できる結果と意味>
- **判断・次の行動**: <結果を受けて選べる操作、引き継ぎ先、復旧・再実行の扱い>
- **業務ルール・制約**: <判定規則、禁止事項、責任分界など。該当しない場合は削除>

#### Scenario: REQ-001-S01 <条件と期待結果が分かる日本語の正常系名称>

- **GIVEN** <開始時の状態・前提データ・利用者権限>
- **WHEN** <利用者または外部システムの単一の操作・イベント>
- **THEN** <利用者または外部システムから観測可能で、合否を判定できる結果>
- **AND** <通知、保存状態、結果の意味、次に可能な操作など、必要な追加結果>

#### Scenario: REQ-001-S02 <業務に影響する日本語の例外系名称>

- **GIVEN** <入力不備、処理失敗、未判定、権限不足などの前提>
- **WHEN** <利用者または外部システムの単一の操作・イベント>
- **THEN** <エラーや未判定の理由、状態変更の有無、保持されるデータなど、確認できる結果>
- **AND** <修正、再実行、復旧、問い合わせ、後続業務への引き継ぎなど、次に可能な行動>

<!--
機能要件は `REQ-001`、非機能要件は `NREQ-001` の形式で記載する。ID はプロジェクト内で一意とし、
採番後に再利用・再採番しない。Scenario は `<要件ID>-S01` 形式にする。各 Requirement に最低1つの
Scenario を記載する。正常系に加え、入力不備、処理失敗、未判定、再実行、境界値、権限不足のうち
業務フローに影響するものを検討し、結果と運用上の扱いを Scenario で明らかにする。該当しない観点は
理由を示して省略でき、例外系を形式的に捏造しない。

Scenario 見出しは必ず `####` (ハッシュ4個) にする。GIVEN は不要なら省略できるが、WHEN と THEN は
必須とする。THEN は「成功する」「エラーになる」だけで終わらせず、利用者が確認できる表示・応答・
保存状態・通知・拒否理由と、必要な次の行動を明記する。

非機能要件も、利用者・運用者が確認できる品質結果として記述する。性能なら対象データ・測定条件・
上限、セキュリティなら許可・拒否の条件と記録、可用性なら失敗時の状態と復旧条件を明記する。
案件固有の数値や承認者が未確認なら推測せず、「未決事項」に記載する。
-->

## MODIFIED Requirements

<!--
既存 capability の振る舞いを変更する場合だけ使用する。既存仕様から `### Requirement:` から配下の
全 Scenario までを完全にコピーして更新する。要件名は既存仕様と完全一致させる。差分だけの抜粋は禁止する。
更新後も、対象者、利用場面、受け取る結果、例外時の扱い、判断・次の行動が読み取れることを確認する。
-->

## 試験方針

<!--
要件ごとではなく、要件区分ごとに試験方針を定義する。実装変更を伴う全 Scenario には自動テストコードを
必須とする。手動試験は補助であり自動テストの代替にしない。非開発者が確認する受け入れ結果がある場合は、
試験パターンに含める。文書のみの変更等で対象外とする場合は、design.md の「試験例外」に理由、承認者、
期限を記録する。
-->

| 要件区分 | 試験層 | 試験パターン | 自動化方針・利用者が確認する結果 |
| --- | --- | --- | --- |
| 機能要件 | unit / integration / e2e | 正常系、異常系、境界値、権限制御、復旧・再実行のうち該当するもの | 実装変更を伴う全 Scenario を pytest 等で自動検証し、<表示・通知・保存状態などの確認結果>を残す |
| 非機能要件 | unit / integration / performance / security | 合意した条件での閾値、負荷、失敗、復旧のうち該当するもの | 自動実行可能な検証を必須とし、<測定値・判定結果・運用記録>を確認できるようにする |
