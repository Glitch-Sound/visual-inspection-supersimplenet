# モデル評価仕様

## Purpose

運用者と評価者が型番別モデルを用いて分割画像と元画像の検査結果、異常箇所、未判定および実行環境を追跡し、再撮影・追加評価・再検査・本番利用検討の判断材料を得る能力を提供する。

## Requirements

### Requirement: REQ-009 実行デバイスの自動選択

システムは、学習または検査の開始時に利用可能な対応 GPU がある場合は GPU を選択し、利用できない場合は処理を中止せず CPU を選択して、選択したデバイスを運用者へ表示しなければならない(MUST)。

#### Scenario: REQ-009-S01 GPU を利用する

- **GIVEN** 対応 GPU と必要なドライバが利用可能である
- **WHEN** 運用者が学習または検査を実行する
- **THEN** システムは GPU を選択して処理を実行する
- **AND** 使用したデバイス情報を結果とログへ記録する

#### Scenario: REQ-009-S02 CPU へ切り替える

- **GIVEN** 対応 GPU がない、または GPU を利用できない
- **WHEN** 運用者が学習または検査を実行する
- **THEN** システムは CPU を選択して処理を継続する
- **AND** CPU へ切り替えた理由と使用デバイスを結果とログへ記録する

### Requirement: REQ-010 分割画像のスコア・判定・可視化

システムは、運用者が型番の検査を要求した時に、型番別の単一学習済みパラメータを全分割 ID へ適用し、分割画像ごとの異常スコア、型番別閾値との比較結果および結果画像を保存しなければならない(MUST)。

試験時は閾値算出時と同じ決定的前処理を使用し、AnomalibのPostProcessorを無効にしたSuperSimpleNetの`pred_score`を異常スコアとし、`pred_score >= threshold`を`anomaly`、それ以外を`normal`と判定しなければならない(MUST)。ヒートマップには同じ推論で得たPostProcessor適用前の`anomaly_map`を分割画像サイズへリサイズして使用しなければならない(MUST)。異常と判定した分割画像のヒートマップは型番別設定の表示範囲で色付けし、下限未満の値は下限の色、上限を超える値は上限の色に固定しなければならない(MUST)。同じ表示範囲では同じ異常マップ値に同じヒートマップ色を割り当て、画像ごとの最小値・最大値で色付けを変更してはならない(MUST NOT)。

#### Scenario: REQ-010-S01 正常な分割画像を記録する

- **GIVEN** スコア契約が一致する型番の学習済みパラメータと閾値があり、分割画像の`pred_score`が閾値未満である
- **WHEN** 運用者が `test --model <型番>` を実行する
- **THEN** システムは分割画像のスコアと `normal` 判定を保存する
- **AND** データ拡張を適用せず、入力内容を変更していない結果画像を保存する

#### Scenario: REQ-010-S02 異常な分割画像を可視化する

- **GIVEN** スコア契約が一致する型番の学習済みパラメータと閾値があり、分割画像の`pred_score`が閾値以上である
- **WHEN** 運用者が検査を実行する
- **THEN** システムは分割画像のスコアと `anomaly` 判定を保存する
- **AND** 元の分割画像を左、型番別設定の共通表示範囲で色付けしたヒートマップを同じ画像に重ねた画像を右に、同じ高さで横に並べた結果画像を保存する

#### Scenario: REQ-010-S03 閾値算出と同じ前処理を使用する

- **GIVEN** bilinear補間、antialiasおよびImageNet正規化を設定したSuperSimpleNetがある
- **WHEN** システムが探索、暫定閾値算出または試験推論の入力を生成する
- **THEN** システムはモデルに設定した同一の決定的前処理を使用する
- **AND** 別ライブラリによる近似前処理を併用しない

#### Scenario: REQ-010-S04 画像間で色を比較する

- **GIVEN** 同じ学習済みモデルと表示範囲で検査され、異なる最小値・最大値を持つ二つの異常マップがある
- **WHEN** 運用者が検査を実行する
- **THEN** 両結果のヒートマップ層では同じ異常マップ値が同じ色になり、範囲外の値はそれぞれ端の色になる
- **AND** 画像全体のスコアと判定は表示範囲によって変わらない

### Requirement: REQ-011 元画像単位の判定集約

システムは、元画像に属する分割判定を集約する時に、一つでも `anomaly` があれば元画像を `anomaly`、全分割が `normal` の場合だけ元画像を `normal`、それ以外は元画像を `undetermined` と記録しなければならない(MUST)。

#### Scenario: REQ-011-S01 一つの異常を元画像の異常へ集約する

- **GIVEN** 同じ元画像の分割判定に一つ以上の `anomaly` がある
- **WHEN** システムが元画像結果を集約する
- **THEN** システムは他の分割判定にかかわらず元画像を `anomaly` と記録する

#### Scenario: REQ-011-S02 全分割正常を元画像の正常へ集約する

- **GIVEN** 同じ元画像に必要な全分割が存在し、全ての分割判定が `normal` である
- **WHEN** システムが元画像結果を集約する
- **THEN** システムは元画像を `normal` と記録する

#### Scenario: REQ-011-S03 判定不能を未判定へ集約する

- **GIVEN** `anomaly` はなく、位置合わせ失敗、分割不足、推論失敗その他の理由による `undetermined` または `error` の分割が一つ以上ある
- **WHEN** システムが元画像結果を集約する
- **THEN** システムは元画像を `undetermined` と記録する
- **AND** 原則として再撮影が必要であり、別の扱いは評価者判断であることを結果へ記録する

### Requirement: REQ-012 元画像単位の検査結果契約

システムは、検査対象の元画像ごとに、元画像名、型番、使用した学習済みパラメータ、スコア契約、閾値、使用したヒートマップ表示範囲、各分割 ID・画像名・異常スコア・判定・結果画像・エラー、元画像判定、処理日時、位置合わせ結果、エラー、警告および共通実行記録を機械可読な結果として保存しなければならない(MUST)。
スコア契約のスコア源は`supersimplenet.pred_score`、PostProcessorの有効状態は`false`に限定しなければならない(MUST)。共通実行記録にはコマンド、型番、開始・終了日時、コマンド単位の処理時間、終了コード、終了状態、デバイス、OS・Python、主要依存関係、警告およびエラーを含めなければならない(MUST)。

#### Scenario: REQ-012-S01 追跡可能な JSON 結果を保存する

- **GIVEN** 型番の検査入力が有効で、対象元画像について正常、異常、未判定、または一部分割の推論エラーを含む判定を確定できる
- **WHEN** システムが元画像の検査結果を確定する
- **THEN** システムは必須項目と、使用したヒートマップ表示範囲、各分割の `normal`、`anomaly`、`undetermined`、`error` のいずれかの判定、および `REQ-011` に従う元画像判定を含む JSON を元画像単位で保存する
- **AND** 判定不能な分割の異常スコアを `null` として保存する

#### Scenario: REQ-012-S02 不正な結果契約を拒否する

- **GIVEN** スコア源が`supersimplenet.pred_score`ではない、PostProcessorが有効、ヒートマップ表示範囲が欠落または不正、分割または元画像の判定が列挙値外、共通実行記録の必須項目が欠落、または日時にタイムゾーンがない結果データがある
- **WHEN** システムが元画像単位の検査結果を生成または読み戻す
- **THEN** システムは不正な項目と理由を示して結果契約を拒否する
- **AND** 不正なデータを正常な検査結果として扱わない

#### Scenario: REQ-012-S03 同じstemの元画像結果を区別して保存する

- **GIVEN** 同じstemで拡張子だけが異なる複数の試験元画像がある
- **WHEN** システムが検査結果を保存する
- **THEN** システムは拡張子付き元画像名を含む一意なJSON名と、拡張子付き分割画像名を含む一意な結果画像名を使用する
- **AND** 一方の元画像または分割結果で他方を上書きしない

#### Scenario: REQ-012-S04 不正な試験manifestのパスと対応関係を拒否する

- **GIVEN** 試験manifestの型番が要求型番と異なる、元画像名・分割画像名にパス要素がある、元画像・分割画像が重複する、または分割の元画像参照・IDが不整合である
- **WHEN** 運用者が検査を実行する
- **THEN** システムは不正な項目と理由を示して推論前に拒否する
- **AND** 準備領域および結果ステージング領域外のファイルを読み書きしない

### Requirement: REQ-013 明示的な再検査

システムは、運用者が型番の再検査を明示した時に、対象型番の旧結果画像と旧 JSON だけを削除し、現在の試験入力、モデルおよび閾値から結果を再生成しなければならない(MUST)。

#### Scenario: REQ-013-S01 旧結果だけを置き換える

- **GIVEN** 対象型番の旧検査結果が存在する
- **WHEN** 運用者が明示的な再検査を実行する
- **THEN** システムは対象型番の旧結果画像と旧 JSON を削除して新しい結果を保存する
- **AND** 元画像、型番設定、事前学習重み、学習済みパラメータおよび試験準備済み画像を削除しない

### Requirement: NREQ-001 対象環境と実行記録

システムは、Ubuntu 24.04 LTS および Windows 11 の x86-64、Python 3.13 で学習、推論、結果保存および GPU から CPU への切り替えを実行でき、各コマンドの結果、処理時間、警告・エラー、主要依存関係およびデバイス情報を記録できなければならない(MUST)。

#### Scenario: NREQ-001-S01 対象 OS の実行契約を確認する

- **GIVEN** 対象 OS に固定済み依存関係と有効な小規模試験データが導入されている
- **WHEN** 運用者が分割位置確認から検査までのスモーク試験を実行する
- **THEN** システムは全コマンドの終了状態、処理時間、依存関係の版および使用デバイスを運用記録へ出力する
- **AND** 生成したモデル、画像および JSON を対象 OS 上で読み戻せる

#### Scenario: NREQ-001-S02 GPU 不能時の復旧可能性を確認する

- **GIVEN** GPU 経路を無効化した対象 OS の試験環境がある
- **WHEN** 運用者が学習と検査のスモーク試験を実行する
- **THEN** システムは CPU へ切り替えて完了し、切り替え理由と処理時間を運用記録へ出力する

### Requirement: REQ-016 アプリ生成checkpointの契約照合

システムは、アプリが生成したcheckpointを用いて検査を開始する時に、保存された型番、スコア契約および閾値を読み込み、現在の設定と照合しなければならない (MUST)。

#### Scenario: REQ-016-S01 一致するcheckpointで検査する

- **GIVEN** 型番、スコア契約および閾値が設定と一致するアプリ生成checkpointがある
- **WHEN** 運用者が `test --model <型番>` を実行する
- **THEN** 契約照合を通過し、分割画像の検査が実行される

#### Scenario: REQ-016-S02 メタデータのないcheckpointを拒否する

- **GIVEN** 必要なメタデータを持たないcheckpointがある
- **WHEN** 運用者が `test --model <型番>` を実行する
- **THEN** 必要なメタデータがない理由を示して検査開始前にエラー終了する
- **AND** 運用者は正しい学習成果物を用意して再実行できる

### Requirement: REQ-018 検査用閾値の選択と記録

システムは、運用者が型番の検査を実行した時に、型番設定の検査用閾値が未指定または `null` なら学習由来の暫定閾値を、0以上1以下の数値なら指定値を判定へ使用し、使用値を結果に記録しなければならない(MUST)。

検査用閾値は `optuna_settings.threshold.value` と独立した型番別設定とする。<br />
学習済み checkpoint、最良試行結果、型番設定にある暫定閾値の整合確認は、検査用閾値の指定にかかわらず維持する。<br />
異常スコアが使用閾値と等しい場合は `anomaly` とする。

#### Scenario: REQ-018-S01 検査用閾値が未指定なら暫定閾値を使用する

- **GIVEN** 暫定閾値と整合する学習成果物があり、検査用閾値を指定していない
- **WHEN** 運用者が `test --model <型番>` を実行する
- **THEN** システムは暫定閾値で分割画像を判定し、結果にその使用値を記録する

#### Scenario: REQ-018-S02 明示的な null なら暫定閾値を使用する

- **GIVEN** 有効な暫定閾値があり、検査用閾値が `null` である
- **WHEN** 運用者が検査を実行する
- **THEN** システムは暫定閾値で判定し、結果にその使用値を記録する

#### Scenario: REQ-018-S03 指定した検査用閾値を使用する

- **GIVEN** 暫定閾値と異なる0以上1以下の検査用閾値がある
- **WHEN** 運用者が検査を実行する
- **THEN** システムは指定した閾値で判定し、結果にその使用値を記録する
- **AND** 型番設定と学習成果物に保存した暫定閾値を変更しない

#### Scenario: REQ-018-S04 境界値を使用する

- **GIVEN** 検査用閾値が0または1である
- **WHEN** 運用者が検査を実行する
- **THEN** システムはその値を判定に使用し、スコアが使用閾値に等しければ `anomaly` と記録する

#### Scenario: REQ-018-S05 不正な検査用閾値を拒否する

- **GIVEN** 検査用閾値が0未満、1超、数値以外、または真偽値である
- **WHEN** 運用者が検査を実行する
- **THEN** システムは設定項目と理由を示して推論前に入力不備として拒否し、不完全な検査結果を正常な結果として保存しない

#### Scenario: REQ-018-S06 暫定閾値の不整合を上書き値で隠さない

- **GIVEN** 検査用閾値が有効でも、型番設定・checkpoint・最良試行結果の暫定閾値が一致しない
- **WHEN** 運用者が検査を実行する
- **THEN** システムは不一致を示して推論前に拒否し、成果物の確認を促す

### Requirement: REQ-019 型番別ヒートマップ表示範囲の指定

システムは、運用者が型番の検査を実行する時に、型番別設定に明示したヒートマップ表示範囲の下限と上限を検査画像間で共通して使用しなければならない (MUST)。

下限と上限は有限の数値で、下限は上限より小さくなければならない。異常マップの値域を異常スコアの `0`〜`1` に限定しない。表示範囲は異常スコア、暫定閾値、検査用閾値と独立する。

#### Scenario: REQ-019-S01 有効な表示範囲を使用する

- **GIVEN** 型番別設定に有限の数値で下限が上限より小さい表示範囲がある
- **WHEN** 運用者がその型番の検査を実行する
- **THEN** システムは同じ表示範囲をその検査の全分割画像の可視化に使用する
- **AND** 異常スコアと判定閾値を表示範囲から変更しない

#### Scenario: REQ-019-S02 未指定または不正な表示範囲を拒否する

- **GIVEN** 型番別設定の表示範囲が未指定、片側だけ指定、数値以外、真偽値、非有限値、または下限が上限以上である
- **WHEN** 運用者がその型番の検査を実行する
- **THEN** システムは不正な項目と理由を示して推論前に入力不備として拒否する
- **AND** 不完全な検査結果を正常な結果として保存しない
- **AND** 運用者は表示範囲を修正して再実行できる

### Requirement: NREQ-002 各 CLI の実行内容の可読性

システムは、運用者が `check`、`train-pre`、`train`、`test-pre`、`test` のいずれかを実行した時に、処理対象、現在の処理段階、終了結果、警告とエラーを人が読める形で表示し、既存の機械可読な終了記録と終了コードを維持しなければならない(MUST)。

#### Scenario: NREQ-002-S01 正常終了を理解できる

- **GIVEN** 有効な入力と対象型番がある
- **WHEN** 運用者がいずれかの CLI を実行する
- **THEN** システムは処理対象と段階、終了状態、処理時間、成果物または処理件数を読める形で表示する
- **AND** 標準出力から従来の1件の実行記録 JSON を読み取れる

#### Scenario: NREQ-002-S02 失敗と警告を理解できる

- **GIVEN** 設定不備、位置合わせ失敗、または処理失敗がある
- **WHEN** 運用者が該当する CLI を実行する
- **THEN** システムは対象、理由、終了状態を読める形で表示し、警告とエラーを区別する
- **AND** 既存の終了コードと機械可読な実行記録を維持する

### Requirement: NREQ-003 検査中の元画像進捗の可読性

システムは、運用者が`test --model <型番>`を実行した時に、試験準備済み元画像の処理済み件数と総件数を検査中に標準エラーへ表示し、端末では進捗バー、端末以外では件数表示を用いなければならない(MUST)。

進捗の対象は元画像であり、一つの元画像に属する分割画像の判定集約が終わった時に一件進める。進捗表示は標準出力の実行記録JSONと終了コードを変更しない。

#### Scenario: NREQ-003-S01 端末で検査の進捗を確認する

- **GIVEN** 複数の試験準備済み元画像があり、標準エラーが端末である
- **WHEN** 運用者が`test --model <型番>`を実行する
- **THEN** システムは元画像の処理に応じて処理済み件数と総件数を示す進捗バーを更新する
- **AND** 正常終了時に総件数まで到達し、標準出力には従来の実行記録JSONを一件だけ出す

#### Scenario: NREQ-003-S02 端末以外で検査の進捗を確認する

- **GIVEN** 複数の試験準備済み元画像があり、標準エラーが端末ではない
- **WHEN** 運用者が`test --model <型番>`を実行する
- **THEN** システムは開始時の`0/総件数`から各元画像の処理後まで件数を標準エラーへ表示する
- **AND** 標準出力には従来の実行記録JSONを一件だけ出す

#### Scenario: NREQ-003-S03 未判定や分割エラーを処理済みとして数える

- **GIVEN** 試験元画像の一部に位置合わせ失敗、分割不足、または個別の推論エラーがある
- **WHEN** 運用者が`test --model <型番>`を実行する
- **THEN** システムは元画像単位の結果を確定したものだけ処理済み件数へ加える
- **AND** 警告・エラー・判定結果と終了コードは従来の契約を維持する

#### Scenario: NREQ-003-S04 処理全体の失敗を完了と表示しない

- **GIVEN** 検査の途中で処理全体が失敗する
- **WHEN** 運用者が`test --model <型番>`を実行する
- **THEN** システムは実際に処理した件数を超えて進捗を増やさず、失敗理由と終了状態を表示する
- **AND** 運用者は原因を修正して再実行できる
