# 技術基盤

## 基本方針

- Pythonの実行、依存関係、仮想環境は `pyproject.toml`、ロックファイル、プロジェクトで採用したパッケージマネージャーを正とする。
- 実行時コードはsrcレイアウトに置き、テスト、lint、format、型検査はプロジェクト設定で定義する。
- 新しい依存関係、外部I/O、永続化、非同期処理、Webサーバーなどは、必要性と影響をchangeの設計で判断する。

## 実装の共通原則

- 公開インターフェースと複雑なロジックに型情報を付ける。
- 外部I/O、設定、利用者への表示を責務境界として扱い、業務ロジックをテスト可能に保つ。
- 秘密情報をコード、仕様成果物、ログ、テストデータに含めない。
- エラー時の利用者への結果と、調査に必要な情報を設計で明確にする。

## テストと検証

- テストは `tests/` に置き、正常系、異常系、境界値など仕様で定義した分岐を検証する。
- `spec.md` に試験方針、`design.md` に試験ケース・テスト実装先・網羅性、`tasks.md` にテスト作成と実行のタスクを記載する。
- 試験設計には検証範囲、残る検証、証跡を記録し、テストダブルによる契約確認と実ライブラリ・全CLI・実機・対象OSでの実行を区別する。
- proposal の受け入れ条件に `- AC-001: <条件>` 形式のIDを付け、design の「受け入れ検証」に全IDの検証範囲・条件、方法、残る検証、状態、証跡を対応付ける。
- 実装後は、プロジェクトで定義されたlint、format、型検査、テストを実行する。
- コミット前は `pre-commit` による高速な基礎検査を行い、統合前には `npm run check` を品質ゲートとする。
- 依存関係の脆弱性検査は、案件で承認されたツールと実行環境を選定して追加する。
- changeの任意の時点で、次のコマンドにより要件・試験設計・テストタスクの対応を確認できる。

```bash
uv run --locked python scripts/check_openspec_traceability.py --change <change-name>
```

進行中の全changeを確認する場合は、`--all` を使用する。

既定の `--phase design` は対応と参照書式を検査し、未作成テスト・未完了タスクを許容する。実装後・統合前は `--phase implementation` を指定し、同じPython環境のpytestで参照テストの収集可否も確認する。収集はテスト本体を実行しないが、conftestやimportは実行する。

verify / archive 前は通常 `--phase complete` を指定する。全タスク完了、全受け入れ条件の状態「検証済み」、残る検証「なし」、空でない実在証跡ファイルを必須とする。実機・対象OS等を利用できず受け入れ確認だけが残る場合は `--phase limited-archive` を指定し、change 直下の `archive-deferred.md` にAC-ID、未完了タスク番号、延期理由、実施責任者、再開条件、追跡先を記録する。証跡はリポジトリルート相対パスで記載し、コマンド・手順、日付、環境・版、結果を記録する。検査は証跡の内容や意味的な網羅性を保証しないため、レビューで対象環境と検証範囲を確認する。

制限付きアーカイブでは、実装・自動試験・品質確認を完了し、延期した条件を「未検証」のまま README.md 等のリポジトリ内 Markdown 文書へ引き継ぐ。GitHub Issue や別の spec は必須ではない。残るリスクを提示し、利用者の明示的な了承を得る。重要な未解決事項やその他の未完了タスクがあれば進行中に残す。正式仕様への同期だけが必要ならsyncを使う。保存済み変更は `--all --include-archived` または `--change archive/<保存名>` で明示して検査できる。制限付きで保存した変更は `--phase limited-archive` を指定する。旧成果物の完了検査にはAC-IDと受け入れ検証表を補完する。

この検査はコミットごとには実行せず、設計レビュー、実装前、統合前、verify / archive 前に工程を選んで実行する。
